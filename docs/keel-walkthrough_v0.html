3. Before you start: the preflight check

Six things must be true before Move 1. Run each command; each takes seconds. If one fails, fix it before going further — a missing tool surfaces as a confusing error three moves later.

1

Keel is installed and healthy

Keel's wrappers (keel-compile, keel-run, …) must be on your PATH and the toolchain installed.

source ~/keel/keel.env
keel-smoke

Expect: a run that ends without errors — manifest, wrappers, tool checkouts, and a no-key hello-world compile all pass.

2

The compiler is v0.2.0 (the real Step 2)

v0.1.0 was scaffold-only. You need v0.2.0 — the version with the model-backed row author that produces a real playbook.

git -C ~/keel/tools/compiler describe --tags

Expect: v0.2.0. If you see v0.1.0, run ./install.sh --update-tools from ~/keel.

Codex CLI is installed and authenticated

plan-orchestrator uses Codex to apply each code change. Without it, Move 4 cannot run.

Expect: a version string. If missing, install and sign in to the Codex CLI first.

4

Claude Code is installed and authenticated

gstack skills (/autoplan, /ship) run inside Claude Code, and the compiler's default row author is claude -p.

claude --version

Expect: a version string, signed in.

The product repo exists

4. Pick the first slice — don't build all 16 weeks at once

The Health Data Hub design is a 16-week, 13-step plan. Keel executes one playbook at a time, and a playbook should be a bounded chunk of work. So the first thing to decide is: which slice goes first?

For a first beta test, the warehouse layer is the right slice. It is pure code, deterministic, touches a narrow part of the repo, has a clear "done", and has a natural human gate (a database schema). It does not need any external service, so the loop runs cleanly start to finish.

step 1Mood-log capture (Apple Notes template — not code)
step 2Ingestion smoke test — Oura + 8 Sleep (needs external services)
step 3 ◀Warehouse layer — DuckDB + 5 tables + warehouse.py + Pydantic validation. Your first slice.
step 4Mood-log API loop — FastAPI
step 5Feature engineering — Polars, source reconciliation
6–13Model, counterfactuals, UI, launchd, tests, restore, evaluate
Why the warehouse layer first: it exercises the entire Keel loop — including a real human gate (the database schema) — without any external dependency. Slice 2, the Oura ingestion, is where you will later meet the blocked_external gate (it needs proof that a real device API works). Save that for run two; learn the loop on the clean slice first.

6. The five moves, in order

This is the walkthrough proper. Do them in sequence. Each move shows what it does, exactly what you run, what you get, and where a human (you) has to decide.

1

Plan

gstack · inside Claude Code

Turn the approved design into a reviewed plan with concrete implementation tasks, and bring it into the product repo. gstack's /autoplan runs a CEO / design / engineering / DX review pass over the design and writes out the plan and an approved build brief.

What you run

# Bring the design doc into the repo and make the standard folders
cd ~/health-data-hub
mkdir -p docs/gstack docs/briefs docs/playbooks
cp aeziz-local-AysajanE-health-data-hub-design-20260515-114138.md \
   docs/gstack/health-data-hub-office-hours.md

# In Claude Code, run the review + planning gauntlet
/autoplan docs/gstack/health-data-hub-office-hours.md
What you get: docs/gstack/health-data-hub-autoplan.md (the reviewed plan, with implementation tasks) and docs/briefs/health-data-hub.approved-brief.md (the approved build brief).
Human gate: at the end of /autoplan you confirm the brief is what you actually want built. For the beta test, keep the focus on the warehouse layer — the schema and warehouse.py.
Beta-test watch-point. The compiler in Move 2 can only author rows for files the plan actually names. Make sure the warehouse tasks list concrete paths — e.g. src/db/schema.sql, src/warehouse/warehouse.py, tests/warehouse/…. The design doc already specifies these; just make sure they survive into the autoplan output. A vague plan produces a thin or failed compile — which is Keel telling you to sharpen the plan, not a bug.
2

Compile

keel-compile · the fast lane

Turn the reviewed plan into a markdown_playbook_v1 — the precise, machine-checkable recipe that plan-orchestrator will execute. The compiler parses your gstack docs, asks a model to author the execution rows, validates everything in deterministic Python, and emits the playbook.

What you run

source ~/keel/keel.env
export PRODUCT_REPO="$HOME/health-data-hub"

keel-compile compile \
  --repo-root "$PRODUCT_REPO" \
  --design   "$PRODUCT_REPO/docs/gstack/health-data-hub-office-hours.md" \
  --autoplan "$PRODUCT_REPO/docs/gstack/health-data-hub-autoplan.md" \
  --approved-brief "$PRODUCT_REPO/docs/briefs/health-data-hub.approved-brief.md" \
  --out      "$PRODUCT_REPO/docs/playbooks/health-data-hub-warehouse.playbook.md" \
  --row-author claude \
  --plan-orchestrator-root "$KEEL_PO_ROOT" \
  --human-approved-by "$USER"

What happens inside

parse the docs → a model authors candidate rows as JSON → Python validates them (paths, write-roots, verification commands, no fabricated files) → Python emits the Markdown → plan-orchestrator confirms the playbook is contract-valid. The model never decides anything about safety; Python re-judges every row.

What you get: the playbook at docs/playbooks/health-data-hub-warehouse.playbook.md, plus sidecars (.meta.json, .validation.json, .rows.json, .author_trace.json) that record exactly how it was produced.
If the compile fails — that is normal, not a beta-test failure. The compiler fails closed and writes .compile-failed.* diagnostic files. Open the .compile-failed.validation.json, read why, sharpen the plan (Move 1), and recompile. A failed compile means Keel caught a problem before any code was written — that is the tool working.
3

Review

you — the gate before any code runs

This is the most important move, and it is entirely human. The playbook is a contract: plan-orchestrator will do exactly what it says, no more and no less. Before anything executes, you read it and decide it is right.

What you run

# Confirm the playbook is contract-valid, and list its steps
keel-doctor  --playbook docs/playbooks/health-data-hub-warehouse.playbook.md --format json
keel-run     list-items --playbook docs/playbooks/health-data-hub-warehouse.playbook.md

What to check, row by row

  • Is each action a real, concrete step — not "implement the warehouse"?
  • Are the files right? Does the DuckDB schema row point at the schema file you expect?
  • Are the allowed_write_roots narrow — src/db, src/warehouse, not . or src?
  • Do behavioral rows carry a real verification command (a pytest that proves the change)?
  • Is the order sane — schema before the code that uses it?
The gate: nothing runs until you are satisfied. If a row is wrong, go back to Move 1 or Move 2 and fix the plan — never hand-edit the playbook into something the compiler would not have produced.
4

Execute

keel-run · plan-orchestrator

Now the code gets written. plan-orchestrator runs the playbook one item at a time. Each item runs in its own throwaway git worktree — a sealed copy — so a bad step can never reach your real branch. After each item is built and its tests pass, two independent reviewers (Codex and Claude) audit the exact same evidence.

What you run

cd "$PRODUCT_REPO"

keel-run supervise run \
  --playbook docs/playbooks/health-data-hub-warehouse.playbook.md \
  --next

# watch it, any time, from another terminal
keel-run supervise status --run-id <RUN_ID> --format json
Your first run will likely stop on a clean-environment check. Before executing anything, plan-orchestrator scans for ambient agent config — chiefly ~/.codex/config.toml and ~/.claude/settings.json — and refuses to run if it finds them, so a worker agent can never inherit your personal credentials, MCP servers, or settings. Because you use Codex and Claude, that detection is expected. Read the message it prints, then re-run with the acknowledgment in front of the command: PLAN_ORCHESTRATOR_CLEAN_ENV_CONFIRMED=1 keel-run supervise run …. Setting that variable is you saying "I reviewed this and accept it on my own machine" — so actually read it first.

The in-flight gates — when plan-orchestrator stops and waits for you

awaiting_human_gate. An item asks for your signoff. For the warehouse slice this is likely the DuckDB schema item — a database deliverable. Read the gate packet, then, from your own terminal:

keel-run mark-manual-gate \
  --run-id <RUN_ID> --item <ITEM_ID> \
  --decision approved --by "$USER" \
  --note "Reviewed the schema; the five tables match the design." \
  --evidence-path docs/reviews/warehouse-schema-signoff.md

keel-run supervise resume --run-id <RUN_ID>

blocked_external. An item needs proof from outside the repo. You will not hit this on the warehouse slice — it has no external services. You will meet it on slice 2 (Oura ingestion), where you supply evidence with supervise resume --external-evidence-dir <dir>.

escalated. Something is genuinely wrong (an unfixable finding, repeated failure). plan-orchestrator stops cleanly with a full audit trail. Read the audit reports and decide: revise the playbook, fix by hand, or abandon the run.

What you get: the warehouse layer — schema, warehouse.py, Pydantic models, tests — committed on the branch orchestrator/run/<RUN_ID>, with an audit trail for every item.
The unbreakable rule. Only you, from a terminal no agent controls, can clear a gate with mark-manual-gate. No script, wrapper, or model ever does. This is the line that makes the whole loop safe to run.
5

Ship

gstack · inside Claude Code

The run branch holds finished, audited code. Hand it to gstack to open a pull request and land it. Never ship straight from the orchestrator's run branch — make a normal ship branch first.

What you run

# Make a normal ship branch from the orchestrator run branch
cd ~/health-data-hub
git fetch origin
git checkout -b ship/health-data-hub-warehouse orchestrator/run/<RUN_ID>

# In Claude Code
/review            # a last code review of the diff
/ship              # version, CHANGELOG, opens the PR
/land-and-deploy   # merges the PR
What you get: the warehouse layer merged into main of AysajanE/longevity-analytics. The first slice is real.
One note for this product. The Health Data Hub is local-first — there is no server. "Deploy" here means it runs on your Mac (via launchd, in a later slice). So Move 5 is really review → PR → merge. /canary and remote-deploy steps do not apply yet.

7. After the loop: repeat, and what a good beta test looks like

You just ran all five moves on one slice. That is the whole method. The next slice — the mood-log API, then feature engineering, then the model — is the same five moves again. Plan, compile, review, execute, ship. The loop never changes; only the slice does.

What success means for this beta test

This first run is a test of Keel, not of the Health Data Hub. Judge it on whether the machine behaved — not on whether the warehouse code is perfect.

  • The loop completed — you went from approved design to merged code through all five moves.
  • You saw the audit run — Codex and Claude reviewed each item, and you read their findings.
  • The gates stopped and waited — plan-orchestrator paused at the schema item and did not proceed until you signed off.
  • Every artifact was legible — you could open the plan, the playbook, the audit packets, and understand them.
  • Failures failed closed — if a compile or an item failed, Keel stopped and told you why, in a file, instead of guessing.
A failed compile or an escalated item is not a failed beta test. That is Keel doing its job — catching a problem and refusing to paper over it. The beta test only fails if Keel does something silently or unsafely: ships an unreviewed change, skips a gate, fabricates evidence, or fails without saying why. Watch for those. Everything else is the tool working as designed.

Keep notes as you go — what was confusing, what was slow, where a message could be clearer. That feedback is the real output of a first beta test.
