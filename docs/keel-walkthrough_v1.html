2. Scratchpad: how this playbook is organized

The build has two jobs at once: build the health app and validate the Keel operating model on a real project. This playbook separates the product architecture from the toolchain process so the team does not confuse “what we are building” with “how a slice gets safely built.”

Main sections

  2. Team roles and safety boundaries.
  3. Keel master loop and artifact trail.
  4. Roadmap sliced into executable playbooks.
  5. Per-slice operating procedure.
  6. Health app architecture and data flow.
  7. Model, tripwire, and launch gates.
  8. Command sheet and failure protocols.

What gets visualized

Flowcharts show the idea → playbook → PO → audit → ship loop.

Diagrams show artifact ownership, data architecture, and PO terminal states.

Dashboards show slice risk, lane choice, model gate status, and tripwire actions.

Simplification rule

A playbook is a recipe. A worktree is a sealed copy. A gate is a locked door. Evidence is a file the team can open. If a step cannot be explained that way, it is too vague to run.

Operating principle

The team should prefer a boring failed gate over an impressive unchecked result. Keel’s value is not speed alone; it is reviewable progress.

3. Product truths the team must preserve

These rules are not polish. They are the product. Every gstack plan, compiler row, PO run, audit, and PR must preserve them.

Retrospective only

v1 explains a logged day after the user has logged mood. It does not predict tomorrow and does not recommend interventions.

v1 scope

Correlation, not causation

Use “model contributors” and “associated with.” Avoid “drivers,” “caused,” “you should,” and “what made you tired.”

UI language gate

Local-first

DuckDB on the Mac, home Wi-Fi only, token-gated FastAPI, encrypted snapshots, no hosted backend in v1.

privacy boundary

Oura + mood are required

8 Sleep is optional under the week-2 tripwire. Garmin, Withings, chest strap, nutrition, and action variables are v2+.

dependency rule

Four model features

v1 model uses exactly: total_sleep_min, hrv_z, deep_sleep_pct, prior_day_feeling.

feature gate

No hidden magic output

Below model gates, the UI says “collecting model-ready days” or “model is not yet better than baseline.” Empty output is a trust-preserving result.

trust rule

Words checklist for every UI and API response

Forbidden in v1

  • “biggest drivers”
  • “what made you tired”
  • “you would have felt 7/10”
  • “caused”
  • “you should sleep more”
  • “tomorrow’s feeling prediction”

Use instead

  • “top model contributors”
  • “patterns associated with this rating”
  • “model-estimated change in your past data”
  • “correlation, not proven causation”
  • “retrospective explanation”
  • “insufficient stable signal”

4. Team roles for the first Keel deployment

One person can hold multiple roles, but the role boundaries must be explicit. The biggest operational risk is letting an agent or a convenience wrapper cross a human-only boundary.

Product owner

Owns scope, tripwires, UI language, and final launch decisions. Approves briefs before compile.

gstack gate

Keel operator

Runs keel-compile, keel-run, keel-doctor, and keel-swr. Watches status and keeps run notes.

run control

Gate reviewer

Reads gate packets and records manual-gate decisions from a human-held terminal. This role must not be delegated to a worker agent.

human only

Evidence librarian

Keeps external evidence directories, smoke-test reports, screenshots, sanitized logs, and restore proof organized.

evidence

Security/privacy reviewer

Checks tokens, local network rules, file permissions, logs, quarantine, encrypted snapshots, and raw-data boundaries.

privacy gate

Release owner

Creates ship branches, runs gstack review/ship/land, writes release notes, and closes the slice with a retro.

ship
Non-negotiable: never brief an agent with “complete the run” or “handle whatever approvals are needed.” Use explicit stop wording: “Run until the first awaiting_human_gate or blocked_external, then stop and summarize.”

10. Plan-orchestrator state machine

PO is the execution kernel. It is not the planner and it is not the shipper. Its job is to run a reviewed playbook row by row, verify, audit, and stop truthfully.

12. Data model and schema gates

The warehouse schema is a manual gate because a bad schema creates weeks of downstream confusion. The first code slice should make this schema real and tested.

Core tables

  • sleep_nights — raw normalized sleep per source and sleep date.
  • mood_entries — append-only mood log history.
  • mood_current — one primary mood row per date.
  • daily_features — derived model-ready features.
  • sleep_merge_diagnostics — source reconciliation debugging.

Warehouse slice deliverables

  • src/db/schema.sql
  • src/warehouse/warehouse.py
  • src/warehouse/models.py
  • scripts/setup_permissions.py
  • tests/warehouse/test_schema.py
  • tests/warehouse/test_mood_correction.py

Schema gate checklist

  • Tables match the design exactly: no extra v2 feature columns in daily_features.
  • hrv_z is persisted as the model feature; hrv_avg_ms is display metadata.
  • mood_entries and mood_current support corrections without DuckDB partial unique indexes.
  • No sleep forward-fill flag exists. Sleep is source-selected or missing; missing sleep excludes training rows.
  • Invalid ingest payloads go to data/quarantine/ with file permissions 0600.
  • Raw JSON, secrets, snapshots, quarantine, and warehouse files are gitignored.

What PO should stop for in S01

Manual gate: after generating src/db/schema.sql and before building downstream warehouse insert functions, PO should stop for schema signoff. The gate reviewer compares the schema to the design doc and records a decision.

13. Model gates: when the app is allowed to show “insights”

The design’s statistical discipline is part of the product. The UI must stay quiet until the model earns the right to speak.


Training status

No model fit. Keep collecting mood and sleep data.

Evaluation window

No UI gate yet.

UI output

Show collecting state only.

Gate logic

N_model rangeWhat happensUI behavior
< 30No model fit.“Collecting model-ready days: N/37.”
30–36Model may train internally but has no evaluable UI gate.No contributors, no counterfactuals.
37–43Use a 7-day walk-forward evaluation window.Show output only if baseline gate passes.
≥ 44Use a 14-day walk-forward evaluation window.Show output only if baseline gate and stability gates pass.
Trust rule: a suppressed counterfactual is not a product failure. It is the correct result when data is insufficient, the model fails baseline, or the mutable sleep feature is not stable enough.

14. Tripwires and fallbacks

Tripwires prevent sunk-cost spirals. The team should apply them by date, not by optimism.

Oura ingestion tripwire

Condition: End of week 1: Open Wearables is not producing usable Oura sleep data in less than one weekend of trying.

Fallback: Drop Open Wearables for Oura and implement direct Oura OAuth2 with authorization-code and refresh-token flow. Keep periodic pull, not webhooks.

Keel handling: Treat the smoke result as external evidence. If the ingestion slice reaches blocked_external, supply the local evidence directory with sanitized logs and proof files.

17. Failure modes and what to do

Most first-deployment pain should be treated as useful feedback. The team’s job is to tell safe failure from unsafe behavior.

Safe failures

  • Compiler rejects vague rows or broad write roots.
  • PO stops at a manual gate.
  • PO blocks on external evidence.
  • Dual audit finds a real issue.
  • Model gates suppress output.
  • Tripwire forces Oura-only scope.

Response: inspect evidence, revise the brief/playbook, or apply the fallback.

Unsafe incidents

  • An agent calls mark-manual-gate.
  • A gate is recorded without a real human decision.
  • External evidence is fabricated or browsed for by an agent.
  • Raw health data or tokens enter git or logs.
  • A run branch is shipped directly.
  • UI makes causal or medical-sounding claims.

Response: stop the run, inspect status/doctor/run_state, record incident notes, and restart from a trusted point if needed.

Incident protocol

  1. Stop issuing run/resume commands.
  2. Inspect keel-run supervise status, keel-run status, and keel-run doctor.
  3. Inspect current manual_gate.json, run_state.json, and audit packet paths.
  4. Record whether a real human approved the gate or evidence.
  5. If no real human approval occurred, invalidate the run and restart from a clean playbook/run boundary.
