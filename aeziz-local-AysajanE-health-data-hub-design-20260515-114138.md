## Problem Statement

Aysajan is hyper-health-conscious and owns five separate connected devices that each generate rich health analytics in isolated silos:

- **Oura Ring** — sleep stages, HRV, body temperature, readiness, activity
- **Garmin watch** — workouts, training load, recovery, GPS, heart rate
- **Withings smart scale** — weight, body fat %, muscle mass, BMI
- **8 Sleep mattress cover** — sleep stages, heart rate, temperature regulation, snoring
- **Chest-strap HRM** — accurate heart rate / zone data during training

Each device has its own app, its own dashboards, its own "insights." None of them talk to each other. None of them know how Aysajan actually *feels*. There is no centralized place where this data can be pulled together for cross-device analytics that surface **candidate correlates** of day-to-day feeling.

The user wants a tool that aggregates device data plus subjective mood logs, identifies **patterns associated with** how he feels, and eventually supports forward-looking intervention hypotheses through deliberate N-of-1 experiments. Split into explicit phases:

```text
v1 goal: retrospective model explanation from sleep/state variables.
        Identify candidate correlates. Make no causal claims.
v2+ goal: prospective intervention engine using action variables 
        (dinner timing, workout intensity, environment, etc.)
        validated by structured N-of-1 experiments.
```

"Drivers," "what makes you tired," and "forward-looking recommendations" are deliberately not v1 vocabulary. Those terms imply causal certainty that v1 cannot deliver from observational data on state variables alone. They are reserved for v2+ once intentional experiments and action features exist.

Starting point is personal use; may share with friends or open-source later.

## What Makes This Cool

The headline UX is the **Retrospective Counterfactual Explainer**.

**v1 — what the explainer actually does on the data we collect:**

> "You logged a 4/10 yesterday. Looking at sleep and HRV, the model's top contributors to this rating were: total sleep 6.2h (well below your usual 7.5h), HRV 38ms (below your 7-day average of 52ms). **Holding the other model inputs fixed, the model estimates that a sleep duration nearer your usual upper range would have been associated with a +0.6 to +1.2 point higher rating. This is a correlation in your past data, not proof that more sleep would have caused you to feel better.**"

**Vision — what a future Autopilot tier could do once we collect action variables (dinner timing, workout intensity, room temperature, etc.) AND have run structured N-of-1 experiments:**

> "You felt 4/10 yesterday. Candidate interventions to test next, ranked by evidence from your completed experiments combined with the observational model: shifting dinner earlier (3 prior experiments, mean +0.8 next-morning rating), lighter Z2-only workouts on low-HRV mornings (1 experiment, +0.5), cooler 8 Sleep temperature after 2am (no prior experiment, observational hint only). The Autopilot suggests testing dinner-shift first because it has the strongest experimental support."

This contrast is intentional. v1 has four features and they are mostly **state variables** (what your body measured), not **action variables** (what you can choose to do differently). Honest v1 counterfactuals only vary features the user can plausibly act on. The richer "dinner timing" example becomes possible only after the Autopilot tier collects action features — a v2+ scope.

### Glossary

The word "counterfactual" gets used two ways and they answer different questions:

- **Retrospective counterfactual** (yesterday-facing, **v1 scope**): "Given the inputs from yesterday, if X had been Y, what would the model-estimated rating have been?" Used to explain what the model associated with yesterday's logged rating. Does NOT claim X caused yesterday's rating.
- **Prospective counterfactual** (tomorrow-facing, **v2+ Autopilot scope**): "Given tonight's known inputs, what change to tonight's controllable inputs maximizes tomorrow's predicted rating?" Used by a future Autopilot tier to propose interventions.

**v1 ships ONLY the retrospective explainer.** No tomorrow predictions, no prospective counterfactuals, no morning forecasts. Prospective recommendations are exactly where nocebo, false precision, and causal overreach become most dangerous — they wait until the Autopilot tier introduces real experimentation discipline and action features.

### Calibration on framing

This is consumer-grade model attribution, not research-grade causal inference. SHAP values and ridge coefficients explain the model's prediction, not the world's causation. Confounders will fool us (stress → late dinner AND bad mood). The doc and UI must consistently frame outputs as "correlations the model found in YOUR past data," never as proven causes. Real causal claims require intentional experiments, which the Autopilot tier introduces later.

Vendor AI coaches (Oura Advisor, Whoop Coach, Garmin Health) architecturally cannot do cross-device fusion because each vendor sees only their own data. That's the structural moat.

The 10x vision — locked via D9 in the office-hours session — is a **hybrid Autopilot + Coach**:

- **Autopilot side** (prospective, interventional): each evening, the system proposes tomorrow's highest-leverage interventions. *"Tonight: dinner before 7:15, 8 Sleep temp -1.5°C after 2am, no zone 4 tomorrow. Expected morning feeling: 7.3. Confidence: medium."* Runs N-of-1 experiments over time to validate which interventions actually move the needle for Aysajan specifically.
- **Coach side** (conversational, explanatory): user can ask *"why am I tired today?"* and get a multi-factor explanation in plain English. Coach can proactively flag: *"your HRV pattern this week looks like the lead-up to your last cold; want to back off training?"*

Both layers share the same backend (data warehouse + feature store + counterfactual model). They differ only in UX surface.

## Constraints

- **Personal use first.** No multi-tenant infra, no compliance gates, no scale concerns.
- **Local-first / user-owned data.** No cloud lock-in, no third-party data brokers. DuckDB on the user's Mac. Backups to iCloud Drive (encrypted with `age`, or via Advanced Data Protection).
- **Reuse plumbing.** Use Open Wearables (`github.com/the-momentum/open-wearables`) for device ingestion where supported; use community-built `pyEight` for 8 Sleep. Don't reinvent OAuth and provider adapters.
- **Sleep stack MVP first.** **Oura + mood log are required for v1.** 8 Sleep is included if `pyEight` ingestion is stable by end of week 2 (per Tripwires); if not, ship Oura-only as a first-class path, not a disappointing exception. Garmin / Withings / chest HRM deferred to v2.
- **Mood-log UX must be sustainable.** A daily mood log that takes >30 seconds will not survive. Target: one tap on phone home screen via iOS Shortcut. **MVP frequency: 1x/day (evening reflection).** Multi-daily logging deferred to v2 once the once-a-day discipline is proven sustainable for 30 consecutive days.
- **Network access:** v1 default is **home Wi-Fi only** for the mood-log iOS Shortcut. Simplest possible path; eliminates Tailscale + Shortcut + iOS-sleep fragility from the critical path. If 30-day usage proves it's too constraining (mood-logging missed because you weren't home in the evening), upgrade to Tailscale post-v1. Single decision saves an entire category of debugging.
- **Statistical floor:** with `N_model` < 30 model-ready days (see "N_model definition" below), ridge will overfit. v1 model uses exactly **4 features**: `total_sleep_min`, `hrv_z` (z-score against prior-only baseline; `hrv_avg_ms` is display metadata only), `deep_sleep_pct`, `prior_day_feeling`. Workout zone time / training load deferred to v2 (requires Garmin). Feature expansion deferred until `N_model` ≥60.

- **`N_model` definition (CRITICAL — used by all gates):**
  ```text
  N_model = count of `daily_features` rows where ALL of these are non-null:
    - primary mood label (via mood_current → mood_entries join)
    - total_sleep_min
    - hrv_z  (may be NULL for the first ~7 days while baseline accumulates)
    - deep_sleep_pct
    - prior_day_feeling (either logged or imputed-for-inference flag set)
  ```
  Using `N_model` (not generic paired-day count) ensures gates fire only when the model has complete inputs. The UI's collection-progress message reads *"Collecting model-ready days: N/37"* (37 is the UI-display threshold; 30 is the internal train threshold — see Baseline Gating § window math for why).
- **Honest uncertainty.** Counterfactuals must surface confidence intervals; predictions must avoid false precision. A "your sleep score will be 73 tomorrow" claim with no uncertainty erodes trust the first time it's wrong.
- **Solo build, weekends + evenings.** No team, no full-time hours. **~6-10 hours per week realistically available, ~96-160 hours total over the 16-week plan** (low end = 6×16, high end = 10×16). All "X weeks" references in this doc are calendar weeks on that solo schedule, not full-time equivalents. **Honest acknowledgment:** the external expert review estimated 140-210 hours for this scope. The doc's 96-160 range is at the optimistic end of that. The mitigation isn't "less work" — it's "if week 9 baseline gate fails, halt feature work and let data accumulate," which defers ~30 hours of UI polish work into the contingency window.

## Premises (agreed in session, D7)

1. **The wedge is the 4-way combo:** multi-device fusion + counterfactual explanation as headline UX + subjective mood as dependent variable + user-owned/local-first storage. Drop any one and you're rebuilding an existing tool.
2. **Open Wearables is the right ingestion layer to reuse,** not rebuild. Your value-add is the analytics and coaching layer above it. Caveat: their docs say Oura "Coming soon" but May 2026 release notes claim webhooks exist — **verify before betting MVP on it.**
3. **Sleep stack first** (Oura + mood log required; 8 Sleep if stable) because sleep is consistently associated with same-day feeling in observational studies and both devices have known-good API paths.
4. **The mood-log UX is on the critical path, not an afterthought.** Without labels, the device data has nothing to correlate with.
5. **Local-first / user-owned data is part of the wedge,** not a future feature. Vendor coaches exist already; the user-owned approach is what makes this different.
6. **Distribution plan exists even for personal use:** reproducible setup, automated daily sync, backups, recovery path.

## Cross-Model Perspective

Codex (running with xhigh reasoning) was invoked in Phase 3.5 as an independent reviewer. Key contributions:

- **Reframed the 10x** from "AI Health Coach" to "Personal Physiology Autopilot" — a self-experiment engine that observes, predicts, intervenes, and learns, rather than a conversational chat coach. *"The magic is not 'why am I tired?' The magic is 'what should I change tonight, and how sure are we?'"* This led to the hybrid framing (D9) where Autopilot proposes interventions and Coach explains them.
- **Identified the real pull:** quoting back the user's own words — *"If you'd eaten dinner 2 hours earlier, predicted feeling: 7/10."* — Codex argued this reveals the user wants *counterfactual control over future state*, not aggregation or chat per se.
- **Validated Open Wearables as the 50% foundation** with a sharp caveat: their provider docs list Oura as "Coming soon" but their May 11, 2026 release post claims Oura + Strava webhooks exist. *Verify with a smoke test before betting MVP on it.* 8 Sleep is not on their roadmap; use `pyEight` (`github.com/mezz64/pyEight`) or `eightctl`.
- **Concrete pragmatic stack proposal:** Python 3.12 + FastAPI + Streamlit + DuckDB + Parquet + launchd cron. Ridge regression / random forest + SHAP for attribution. Constrained grid search for counterfactuals (simpler than DiCE; sufficient for personal scale).
- **Surfaced two failure modes** we had not discussed:
  - **(a) Fake causality.** SHAP explains the model's prediction, not the world's causation. Stress can cause both late dinner AND bad mood, producing a misleading SHAP value. To get real causal claims you need randomized personal experiments — the autopilot tier is partly there to handle this.
  - **(b) Mood-label contamination / nocebo loops.** Once the app predicts "you should feel bad," a hyper-health-conscious user may rate themselves worse, turning the system into a score-chasing trap. UX must be careful about uncertainty framing and intervention burden.

## Approaches Considered

### Approach A: Weekend MVP (Codex's pragmatic plan)

Single Streamlit page showing yesterday's mood, top SHAP contributors, one retrospective counterfactual, confidence warning. iOS Shortcut for mood logging. launchd cron pulls Oura + 8 Sleep data daily. Built in 1-2 weekends. No FastAPI initially; no autopilot; no coach. Retrospective explainer only.

- Effort: S (1-2 weekends, ~25-40 hours)
- Risk: Low
- Pros: Ships fast, validates the whole loop cheaply, easy to iterate
- Cons: No coach or autopilot; Streamlit ceiling is real; harder to evolve into the hybrid 10x without a refactor

### Approach B: Layered Backend + Streamlit (selected)

Six-layer architecture from day 1: Ingestion → Warehouse → Feature Store → Model → API → UI. FastAPI is real (not vestigial); Streamlit consumes it. Polars for feature engineering. Pydantic models for the API contract. Pluggable model layer so SHAP attribution + counterfactual search can evolve independently. Architecture explicitly designed so the Autopilot tier (scheduled jobs reading from the API and delivering interventions) and the Coach tier (LLM-with-tools agent calling the API) can be added in v2/v3 without rewrites.

- Effort: M (~96-160 hours total over 16 calendar weeks of solo evenings/weekends, at 6-10 hr/wk)
- Risk: Medium
- Pros: Architecture supports the full hybrid 10x; API surface is reusable for mobile companion later; clean layer separation enables independent evolution
- Cons: 2-3x build time vs A; risk of over-engineering before validating loop; "ideal architecture" trap of polishing forever

### Approach C: Daily Health Newsletter (calm-tech lateral)

"The app you don't open." Every morning at 6am, an email arrives: yesterday's feeling + counterfactual, today's predicted feeling, today's one experimental nudge, weekly trends as embedded charts. Mood logging via iOS Shortcut. Backend is cron + Python + Jinja + smtplib + DuckDB. No web UI at all.

- Effort: S-M (2-3 weeks, ~30-50 hours)
- Risk: Low-Medium
- Pros: Zero app fatigue; calm-tech ethos; lowest UX surface area; the email is shareable with a doctor by definition
- Cons: No bidirectional interaction beyond mood logging; not a "product" you can demo; bolting on a conversational coach later requires a different surface

## Recommended Approach

**Approach B: Layered Backend + Streamlit.**

This was the user's explicit choice in D10. Rationale: the user is committed to the hybrid 10x (Autopilot + Coach) and prefers to build the architecture that scales rather than refactor later. Given the user has stated intent to potentially share with friends later or open-source the project, the API-first architecture also makes that path easier.

### Why FastAPI in v1 (not deferred)

FastAPI is **not** vestigial in v1 because the mood-log iOS Shortcut needs an HTTP endpoint to POST to. Once we're already hosting an HTTP service for that, exposing the read endpoints through the same service costs almost nothing and gives the Autopilot/Coach tiers a real surface to call later. Without the mood-log endpoint, FastAPI would be premature; with it, FastAPI is the simplest thing that works.

**Caveat from Tripwires:** if the iOS Shortcut transport fails the week-4 check, the fallback is a tiny Streamlit-on-home-Wi-Fi mobile form, which removes the need for FastAPI entirely. In that scenario, FastAPI is deferred to v1.1. This is an acknowledged "FastAPI is optional under the fallback path" reality.

### Label Alignment (CRITICAL)

To prevent off-by-one bugs, the v1 target is defined precisely:

- **The evening mood log on date D** asks: *"How did I feel overall today?"* This produces `feeling[D]`.
- **Model target:** `feeling[D]`. The model predicts same-day evening rating from last night's sleep + state.
- **Sleep features for `feeling[D]`** come from the main sleep episode ending on the morning of D, stored as `sleep_date = D` in `sleep_nights`.
- **`prior_day_feeling`** is `feeling[D-1]` — yesterday's rating, used as a lag feature.

We are **NOT predicting tomorrow's feeling from today's sleep** in v1. That's a v2/Autopilot concept. v1 is strictly: *"Given last night's sleep, here is the model's after-the-fact explanation of how you rated today."*

### Mood Prompt Standardization (CRITICAL)

The mood label is the only dependent variable. It must be consistent across weeks 2 and 50, or the model is learning noise from the user's drifting interpretation of "feeling."

**Fixed prompt:** *"How did I feel overall today?"*

**Anchored scale:**
- 1 = terrible / sick / nonfunctional
- 3 = poor
- 5 = normal baseline
- 7 = good
- 10 = exceptional

Anchors are shown in the iOS Shortcut menu every time. No free-form interpretation.

**Optional context chips** (logged but NOT modeled in v1): `sick`, `travel`, `alcohol`, `unusually stressful`, `unusual workout`, `late meal`. These help explain outliers when reviewing manually. They become candidate v2 features only after N≥90 days of usage shows which actually correlate.

### Feature Mutability Taxonomy (CRITICAL)

Each model feature has explicit metadata controlling how it's used in the UI and the counterfactual algorithm. SHAP ranks **what the model found predictive**; mutability tells us **what the user can act on**. These are different and must not be conflated.

| Feature | Role | `mutable` | `recommendation_policy` | `show_as_contributor` |
|---|---|---|---|---|
| `total_sleep_min` | indirectly-controllable behavior | true | `allowed_with_caveat` | true |
| `hrv_z` (model) / `hrv_avg_ms` (display) | physiological state | false | `disallowed` | true |
| `deep_sleep_pct` | noisy derived sleep-stage metric | false | `disallowed` | true |
| `prior_day_feeling` | outcome lag | false | `disallowed` | true |

Enforced in code as a single source of truth:

```python
FEATURES = {
    "total_sleep_min": {
        "role": "behavior", "mutable": True,
        "recommendation_policy": "allowed_with_caveat",
        "show_as_contributor": True,
        "display_name": "Total sleep",
        "unit": "minutes",
        "safe_floor": 420,  # 7 hours; no CF may suggest going below this
    },
    "hrv_z": {
        "role": "physiological_state", "mutable": False,
        "recommendation_policy": "disallowed",
        "show_as_contributor": True,
        "display_name": "HRV (z-score vs baseline)",
        "display_companion": "hrv_avg_ms",  # show ms in UI
    },
    "deep_sleep_pct": {
        "role": "noisy_stage_metric", "mutable": False,
        "recommendation_policy": "disallowed",
        "show_as_contributor": True,
        "display_name": "Deep sleep %",
    },
    "prior_day_feeling": {
        "role": "outcome_lag", "mutable": False,
        "recommendation_policy": "disallowed",
        "show_as_contributor": True,
        "display_name": "Yesterday's feeling",
    },
}
```

Consequences:

- **Top model contributors** can include any `show_as_contributor=True` feature that passes sign-stability.
- **Counterfactuals** vary ONLY features with `mutable=True` AND `recommendation_policy != "disallowed"`.
- For v1 this means **counterfactuals vary `total_sleep_min` and nothing else** (single-feature CF). It is mathematically valid but useless to "counterfactual" HRV — the user cannot choose to have higher HRV.

This is the most important design rule in the doc. Without it, the system generates impressive but absurd suggestions like "if your HRV had been 60 instead of 38, you would have felt better."

### Data Model (v1)

Two raw tables, one derived. All timestamps stored UTC. Home timezone resolved with `zoneinfo.ZoneInfo("Europe/Luxembourg")` (or user's actual home TZ). `sleep_date` is computed at insert time as `waketime_utc.astimezone(home_tz).date()`. DST is handled by zoneinfo automatically.

```sql
-- Raw normalized sleep data, one row per night per source
CREATE TABLE sleep_nights (
    source              VARCHAR NOT NULL,    -- 'oura' | '8sleep'
    sleep_date          DATE NOT NULL,       -- wake date in home TZ
    bedtime_utc         TIMESTAMP,
    waketime_utc        TIMESTAMP,
    total_sleep_min     INTEGER,
    rem_min             INTEGER,
    deep_min            INTEGER,
    light_min           INTEGER,
    awake_min           INTEGER,
    hrv_avg_ms          DOUBLE,
    rhr_avg_bpm         INTEGER,
    body_temp_dev_c     DOUBLE,              -- vs personal baseline
    sleep_score         INTEGER,             -- vendor-provided
    ingested_at_utc     TIMESTAMP NOT NULL,
    PRIMARY KEY (source, sleep_date)
);
-- Note: no is_imputed on sleep_nights — sleep is never forward-filled (see Missing Data Policy).
-- daily_features.prior_day_feeling_imputed is the only imputation flag in v1.

-- Subjective mood entries (append-only history)
CREATE TABLE mood_entries (
    log_id              UUID PRIMARY KEY,
    logged_at_utc       TIMESTAMP NOT NULL,
    mood_date           DATE NOT NULL,       -- the local calendar day BEING RATED (not the date the POST occurred).
                                             -- Computation: mood_date = (logged_at_utc.astimezone(home_tz) - timedelta(hours=4)).date()
                                             -- This keeps late-night logs (00:00-04:00 local) attributed to the previous day.
    feeling             INTEGER NOT NULL,    -- 1-10
    energy              INTEGER,             -- 1-10, optional
    notes               TEXT,
    context_chips       VARCHAR[],           -- optional set: 'sick','travel','alcohol','unusually_stressful','unusual_workout','late_meal','poor_sleep_environment','high_stress'
                                             --   NOT modeled in v1; surfaced in UI for outlier explanation.
    source              VARCHAR,             -- 'ios_shortcut' | 'manual' | 'backfill'
    supersedes_log_id   UUID                 -- if this is a correction, the prior row's log_id
);

-- Current primary mood per day (one row per mood_date; updated on correction)
CREATE TABLE mood_current (
    mood_date           DATE PRIMARY KEY,
    log_id              UUID NOT NULL
);
-- Correction flow:
--   1. INSERT INTO mood_entries (...new row with supersedes_log_id pointing at prior row's log_id if any)
--   2. INSERT OR REPLACE INTO mood_current (mood_date, log_id=new log_id)
-- Training join:
--   SELECT e.* FROM mood_current c JOIN mood_entries e ON e.log_id = c.log_id WHERE e.mood_date >= ...
-- This avoids relying on DuckDB partial unique indexes (which DuckDB doesn't document).

-- Derived daily features, one row per date
CREATE TABLE daily_features (
    feature_date            DATE PRIMARY KEY,
    -- v1 model features (exactly 4)
    total_sleep_min         INTEGER,         -- merged duration: average if agreement, Oura if >60m disagreement, single source if only one
    hrv_z                   DOUBLE,          -- THE feature the model uses; prior-only baseline
    deep_sleep_pct          DOUBLE,          -- Oura only under active v1 provider policy
    prior_day_feeling       INTEGER,         -- mood lag-1
    -- display metadata (NOT model features)
    hrv_avg_ms              DOUBLE,          -- raw ms value for UI display
    hrv_z_method            VARCHAR,         -- 'prior_28d' | 'prior_expanding_min7'
    feature_version         VARCHAR,         -- e.g., 'v1.0' for reproducibility
    -- explicit quality flags (replacing the coarse is_imputed)
    prior_day_feeling_imputed BOOLEAN DEFAULT FALSE,
    sleep_source_count      INTEGER,         -- 1 or 2
    sleep_merge_warning     VARCHAR,         -- e.g. '8sleep_fallback_ignored'
    computed_at_utc         TIMESTAMP NOT NULL
);
```

Raw provider JSON also kept on disk under `data/raw/{source}/{sleep_date}.json` for replay/audit. The DB table is the canonical normalized view; the JSON files are the immutable record.

```sql
-- Diagnostics for sleep source reconciliation
CREATE TABLE sleep_merge_diagnostics (
    sleep_date              DATE PRIMARY KEY,
    oura_present            BOOLEAN,
    eight_present           BOOLEAN,
    total_sleep_delta_min   INTEGER,            -- Oura vs 8 Sleep gap
    hrv_merge_method        VARCHAR,            -- 'oura_primary'|'missing' under active v1 policy
    stage_source            VARCHAR,            -- 'oura' under active v1 policy
    warning                 VARCHAR,            -- e.g. '8sleep_fallback_ignored'
    computed_at_utc         TIMESTAMP NOT NULL
);
```

This table is for debugging when the model says "sleep duration mattered" but the underlying devices disagreed.

**v2 candidate features** (do not add to v1): `days_since_zone4`, `training_load_7d`, `subjective_energy_lag1`, `body_temp_dev_c_lag1`. Reintroduce only when N≥60.

### Sleep Source Reconciliation

S03 provider-policy update, 2026-05-31: the 8 Sleep reconciliation rules in this original design are superseded for v1. 8 Sleep / pyEight is fallback-only; Oura direct API v2 is the first-class sleep provider. Feature construction must ignore 8 Sleep rows for v1 model features even if they exist in the warehouse. Diagnostics may record that 8 Sleep rows were present and ignored under fallback. 8 Sleep must not be averaged, blended, reconciled, used as fallback HRV, used as fallback sleep stage source, or counted as an active sleep source unless a future explicit provider-reopening slice supersedes S03.

Under the active S03 decision, merge into `daily_features` using this priority:

- **Sleep stage breakdown** (deep, REM, light, awake): **Oura only** for v1. 8 Sleep staging is not a fallback source under the active S03 decision.
- **`deep_sleep_pct` computation:** `Oura.deep_min / Oura.total_sleep_min` when Oura is present. If only 8 Sleep is present, leave the v1 model feature unset.
- **HRV (RMSSD):** Oura only for v1. Store per-source HRV in `sleep_nights.hrv_avg_ms`; the `daily_features` row uses Oura's HRV when present and otherwise leaves v1 HRV features unset. The `sleep_merge_diagnostics.hrv_merge_method` column records `'oura_primary'` or `'missing'` under the active S03 decision.

  The MODEL trains on the persisted `hrv_z`. UI displays `hrv_avg_ms` in ms. **Persisting `hrv_z` (rather than recomputing) makes restore reproducible.**

  **`hrv_z` computation (CRITICAL, prior-only to avoid future-data leakage; robust z-score):**

  ```text
  Use only days strictly BEFORE feature_date.
  Robust z formula: hrv_z[D] = (hrv_ms[D] - median(prior)) / (1.4826 × MAD(prior))
    The 1.4826 scaling makes the result comparable to a standard z-score under normality.

  Method 1 (default, prior 28-day window):
      hrv_z_method = "prior_28d"

  Method 2 (prior expanding window with min 7 values, used for first few weeks):
      hrv_z_method = "prior_expanding_min7"

  Zero-MAD fallback (MAD ≈ 0 means HRV was constant in the window):
      If MAD < 1e-6, fall back to standard deviation: hrv_z = (x - mean) / std.
      If std also < 1e-6, set hrv_z = NULL and exclude row from training.
      Log fallback method in hrv_z_method as 'prior_28d_std_fallback' or similar.

  If fewer than 7 prior HRV values exist, set hrv_z = NULL and exclude row from training (and from N_model).
  ```

  Persisting `hrv_z` (rather than recomputing in-memory) makes the model reproducible from disk — a snapshot restore renders the same numbers. `feature_version` lets us detect when the computation changed and trigger a recompute.
- **Total sleep duration**: use Oura only for v1. If both Oura and 8 Sleep rows exist, keep Oura and record the Oura vs 8 Sleep gap only as diagnostics. If only 8 Sleep is present, leave v1 sleep model features unset.
- **Body temperature deviation and resting HR are NOT v1 features.** They are stored in `sleep_nights` if the provider supplies them, but there is no `body_temp_dev_c` or `rhr_avg_bpm` column in `daily_features` and they are not in the v1 model. They are candidate v2 features once `N_model ≥ 60`. (Earlier drafts listed reconciliation rules for these — those rules apply only when v2 introduces the columns.)

Reconciliation logic lives in `src/warehouse/features.py` and `src/warehouse/warehouse.py` and is unit-tested with fixtures for: both-present ignored fallback, Oura-only, and 8Sleep-only fallback rows.

### Missing Data Policy

- **One sleep source missing, other present:** Oura-only rows are eligible. 8 Sleep-only rows do not create v1 sleep model features under the active S03 fallback decision. Record the source-coverage state in `sleep_merge_diagnostics`.
- **Both sleep sources missing:** **do NOT forward-fill for training.** Forward-filling sleep across days creates fictional observations and manufactures spurious correlations. Skip the row entirely for model training. For UI-only display, optionally show the prior day with a "no sleep data captured" label — never a numeric estimate.
- **`prior_day_feeling` missing (yesterday had no mood log):**
  - **For model training:** exclude the row entirely. Do NOT train on imputed lag values at small N; a few imputed lag values can materially distort a model trained on 30-60 days.
  - **For display/inference only:** if needed to render an insight for a day where the *prior* day's mood is missing, impute using the 7-day rolling mean and set `prior_day_feeling_imputed=True`. UI forces `confidence_label` down one bucket on any insight with an imputed prior-day value.
- **Mood log missing (as label)**: do NOT impute. Mood is the label. Days without a mood log are excluded from training entirely.
- **Data freshness shown in UI**: `/api/health` returns `data_freshness` per source. `/api/insights/{date}` and `/api/insights/latest_logged_day` include it in the response payload. If any source is >36h stale, surface a warning banner in Streamlit.

**Bind + auth policy — Option B "same-host only" (one FastAPI process, middleware-enforced):**

The "localhost-only reads" framing from earlier drafts doesn't survive contact with Uvicorn: binding to `LAN_BIND_IP` means `127.0.0.1` isn't listening, so Streamlit's localhost calls would fail; binding to `0.0.0.0` widens the threat surface to all interfaces including any VPN. **Option B** binds to the Mac's home-Wi-Fi LAN IP and allows reads from clients whose source IP matches either loopback OR the same LAN IP. The remote phone (separate LAN IP) gets 403'd; the Mac itself (whether Streamlit calls via `LAN_BIND_IP` or via loopback if the OS routes it that way) is allowed.

`LAN_BIND_IP` is set explicitly in `.env`, not resolved at startup (`socket.gethostbyname(socket.gethostname())` is unreliable on macOS). README documents how to find the Mac's home-Wi-Fi LAN IP and recommends a DHCP reservation or a stable `.local` hostname in the Shortcut for stability.

```python
from fastapi import Depends, FastAPI, Header, HTTPException, Request
from fastapi.responses import JSONResponse
import os, secrets

app = FastAPI()
ALLOWED_READ_CLIENTS = {"127.0.0.1", "::1", os.environ["LAN_BIND_IP"]}

@app.middleware("http")
async def restrict_reads_to_same_host(request: Request, call_next):
    if request.method == "GET" and request.url.path.startswith("/api/"):
        if request.client.host not in ALLOWED_READ_CLIENTS:
            return JSONResponse(status_code=403, content={"detail": "Reads same-host only"})
    return await call_next(request)

# Token validation, constant-time compare (defense against timing leakage on LAN)
async def require_token(x_mood_token: str = Header(...)):
    if not secrets.compare_digest(x_mood_token, os.environ["MOOD_TOKEN"]):
        raise HTTPException(status_code=401, detail="Invalid token")

@app.post("/api/mood", dependencies=[Depends(require_token)])
async def post_mood(...): ...

@app.get("/api/insights/{date}", dependencies=[Depends(require_token)])
async def get_insight(...): ...
```

### Model Lifecycle

- **v1 default:** sklearn `Ridge(alpha=1.0)` on StandardScaler-transformed features. `alpha=1.0` is a chosen default, not magic. Optional refinement at N≥45: tiny `RidgeCV` over `[0.1, 1.0, 10.0]` with leave-one-out evaluation. Don't optimize alpha before then — variance in CV at small N exceeds the gain.
- **Two launchd plists:** (a) `health.sync.plist` at 8am pulls Oura + 8 Sleep data and recomputes `daily_features`. (b) `health.retrain.plist` at 11pm retrains the model on whatever data has accumulated, including that evening's mood log. Separate plists because morning sync and evening retrain have different inputs and failure modes. **First-run safety:** the retrain script no-ops gracefully when N<30 paired days — it logs `{"n_paired_days": N, "skipped": true}` to `eval.jsonl` and exits 0. No model file required to exist before that point.
- **Retrain cadence:** evening plist retrains on all-history; persists to `models/ridge-{date}.pkl` alongside the fitted scaler. Walk-forward residuals logged to `models/eval.jsonl`.

**`eval.jsonl` record schema** (one JSON object per line, written nightly):

```json
{
  "date": "2026-05-15",
  "n_model": 32,
  "ridge_walk_forward_rmse": 1.42,
  "baseline_rolling_mean_rmse": 1.55,
  "baseline_prior_day_rmse": 1.61,
  "ridge_better_day_count": 9,
  "n_eval_days": 14,
  "baseline_gate_passed": true,
  "ablation_prior_mood_only_rmse": 1.58,
  "ablation_sleep_features_only_rmse": 1.47,

  "feature_version": "v1.0"
```

#### Baseline gating (CRITICAL)

Before the UI shows any SHAP contributors or counterfactuals, ridge must demonstrably beat two simple baselines under walk-forward evaluation:

1. **Rolling 7-day mean of feeling.** Predict day D as the mean of `feeling[D-7..D-1]`.
2. **Prior-day feeling.** Predict day D as `feeling[D-1]`.

**N_model-dependent evaluation window:**

```text
N_model < 30:       no model fit, no gate, no UI of model output.
30 ≤ N_model < 37:  model can train internally, but no UI gate yet — collect eval days.
37 ≤ N_model < 44:  eval window = last 7 days. Each fold trains on ≥30 prior model-ready days.
N_model ≥ 44:       eval window = last 14 days. Each fold trains on ≥30 prior model-ready days.
```

Gate criteria (both must hold to pass):

```text
ridge_walk_forward_rmse ≤ 0.95 × min(rolling_mean_rmse, prior_day_rmse)
AND
ridge_better_day_count ≥ ceil(0.65 × n_eval_days)
  (ridge had lower absolute error than best baseline on ≥65% of eval days)
```

The day-count requirement prevents one outlier day from making RMSE look artificially good.

UI rule: if gate fails, display *"Model is not yet better than a simple baseline. Collecting more data."* No contributors, no counterfactuals. Re-evaluate nightly. The model "earns the right" to show its outputs each night.

**Ablation logging** (for visibility into whether sleep features add value beyond mood autocorrelation):

```text
For each nightly eval, log to eval.jsonl:
  ridge_all_features_rmse
  ridge_prior_mood_only_rmse
  ridge_sleep_features_only_rmse
```

If `ridge_all_features_rmse` ≈ `ridge_prior_mood_only_rmse`, the sleep features aren't contributing and the model is mostly mood autocorrelation. That's a critical signal.

#### Coefficient stability — bootstrap sign stability

The earlier "ridge SE heuristic" doesn't work well — ridge coefficients are biased by design and analytical SEs are misleading. v1 uses **bootstrap sign stability** instead:

1. Resample the training set 200 times with replacement (**resample on `feature_date` with replacement** — at v1 there's one row per date so this is equivalent, but the rule matters if multiple rows per date ever exist).
2. Refit ridge each time.
3. For each feature, count fraction of resamples where the coefficient has the same sign as the point estimate.
4. **Stability tiers (stricter than the prior 70% threshold to suppress fragile signals):**
   - **≥90%:** show normally as a top model contributor.
   - **80-89%:** show with an explicit "low-confidence signal" label.
   - **<80%:** suppress entirely.

Display rules (reconciling with counterfactual rules):

- **Top contributors list:** show any feature meeting the ≥80% threshold. If zero survive, display *"Insufficient stable signal — collecting more data."* The "fewer than 2" rule from a prior revision is dropped — a single stable contributor is informative.
- **Counterfactual:** runs if **at least one feature with `mutable=True` AND `recommendation_policy != "disallowed"` is sign-stable at ≥90%**. The "fewer than 2 features" rule does NOT block the counterfactual when the one stable feature is the mutable one.

200 resamples × ridge on N=30 features=4 is <1s on a Mac. Cheap enough to run nightly.

**Calibration note:** at N=30 with 200 bootstrap resamples (each omitting ~37% on average → N_eff ≈ 19), the 90% threshold may be hard to meet. If no features survive ≥90% by week 12, revisit the threshold (consider dropping to 85% for the contributor display only, keeping ≥90% for counterfactual gating).

#### Prediction intervals (conservative)

Bootstrap residuals (200 samples) on training set → 90% prediction interval. Define **`full_width = ci_high - ci_low`** consistently throughout. **Conservative minimum full-width rule until N≥60:** never display a full-width narrower than 2.0 mood points (i.e., always at least ±1.0 point each side).

Bucketed for UI:

- **high:** `full_width ≤ 2.0`
- **medium:** `2.0 < full_width ≤ 3.5`
- **low:** `full_width > 3.5`

Because the minimum is 2.0, "high" requires `full_width = 2.0` exactly (the floor). This is intentional — the high bucket is only reachable when N is large enough that bootstrap residual width naturally drops to the floor.

UI always shows the bucket prominently; the numeric interval is secondary.

#### R² expectations (softened)

Honest framing: with personal mood data, low R² doesn't necessarily mean the feature set is wrong. It can mean:
- mood labels are noisy or anchored inconsistently
- there hasn't been enough behavioral variation to identify drivers
- unmeasured factors (stress, illness, travel, alcohol) dominate
- N=30 is simply too small

**Better gate than a specific R² target:** at N=30, evaluate whether ridge beats the baselines above in walk-forward prediction. That's the meaningful question. Track R² in `eval.jsonl` for visibility but don't make it a UI claim.

#### Drift detection (deferred from UI)

Walk-forward residuals logged nightly. **Not surfaced in the UI in v1** — a single illness or travel week can produce false-positive drift signals at small N. UI-level drift detection deferred until N≥90.

#### Early-N degradation mode (CRITICAL)

Below `N_model = 37`, predictions and counterfactuals are NOT shown. UI displays: *"Collecting model-ready days: 17/37. Insights begin once we have 37 model-ready days."* (37 not 30 because the eval window math at N_model=30 produces 0 evaluable days; gating begins meaningfully at N_model=37.)

At `N_model ≥ 37`, **the baseline gate** above takes over — the model still has to beat baselines to show insights. Better to defer the magic moment by another week than to ship hallucinated counterfactuals.

**Implementation reminder (written down so it can be enforced during build):**

> A suppressed counterfactual is not a product failure; it is a trust-preserving outcome. Do not weaken gates because the UI is empty.

### Counterfactual Algorithm (v1 — single-feature, mutability- and safety-gated)

Runs only when ALL of the following hold:

- (a) `N_model ≥ 37` (baseline gate begins evaluating here; see Baseline Gating § window math)
- (b) baseline gate passed for this date
- (c) at least one feature with `mutable=True` AND `recommendation_policy ∈ {"allowed", "allowed_with_caveat"}` is sign-stable
- (d) the bootstrapped delta interval excludes "trivial improvement" thresholds (see step 6)

For v1, the only feature meeting (a-c) is `total_sleep_min`. The algorithm is a **single-feature 1D scan**:

1. Identify mutable + recommendable + sign-stable features. Call the chosen feature `f`. (v1: always `total_sleep_min`.)
2. Compute `f`'s **unconditional 5th-95th percentile** from `daily_features` history — the "realistic perturbation envelope."
3. Add **direction and safe-floor constraints**:
   - **Increase-only:** v1 counterfactuals for `total_sleep_min` may only consider *increasing* sleep duration. Never propose a candidate below yesterday's actual value. Even if ridge learned a negative coefficient (confounded by illness/recovery days correlating with long sleep), we don't surface "you'd have felt better with less sleep" — that's actively harmful for a sleep-conscious user and contradicts CDC/AASM adult-sleep guidance.
   - **Safe floor:** candidate must be ≥ 420 minutes (7 hours, per CDC/AASM consensus for adult sleep; configurable per user).
   - **Threshold check:** if actual sleep yesterday was already ≥ user's recent median total_sleep, suppress the counterfactual ("no useful sleep-increase suggestion — yesterday's sleep was already at your normal upper range").
4. Generate 10 candidate values within the envelope ∩ [safe_floor, 95th_pct].
5. **Plausibility filter (corrected):** for each candidate, build the **full candidate vector** by substituting `x_cand` for `f` while keeping all other features at yesterday's values. Compute standardized Euclidean distance from this full candidate vector to its nearest historical day (excluding the target day itself). Reject if distance > 2.0 standardized units. *This is different from the prior version which excluded `f` from the distance — that defeated the purpose because the candidate would always equal yesterday on the remaining features.*
   - Additional plausibility check: at least one historical day must have similar HRV/deep-sleep/prior-mood context AND `total_sleep_min` within ±30 minutes of the candidate. If no such day exists, the candidate is suppressed.
6. Predict feeling for each surviving candidate. Compute **bootstrap delta interval** (90% CI):
   ```text
   For each of 200 bootstrap resamples of training days:
     refit scaler + ridge
     compute predicted_delta = pred(candidate) - pred(actual)
   Return 5th and 95th percentiles of predicted_delta → (model_delta_low, model_delta_high)
   ```
   This answers "how uncertain is the model-estimated change between actual and counterfactual?" — distinct from a residual-based prediction interval which would answer "what range of actual moods might occur."
7. **Trivial-effect suppression:** reject if `model_delta_low ≤ 0` (interval crosses zero) OR `median(deltas) < 0.5` mood points (effect too small to be meaningful).
8. Return the candidate that maximizes `(median_predicted_delta − λ × |x_cand − x_actual| / scaler.scale_[f])` with `λ = 0.1`. λ penalizes large jumps from yesterday's actual value, scaled in standard deviations of `f`.
9. Render as: *"Looking at days with similar HRV and deep-sleep context, the model estimates that a `{feature_display_name}` of `{comparison_value}` (vs your `{actual_value}` yesterday) was associated with a +{model_delta_low} to +{model_delta_high} point higher rating. This is a correlation in your past data, not proof of causality."*
10. Always include the causal caveat. Always include the delta interval, not a point estimate.

**If step 7 (trivial-effect suppression) fires:** show *"The estimated change is too uncertain to call useful."* No counterfactual rendered.

**Multi-feature counterfactuals deferred to v2** — they introduce joint-implausibility risks and require a user-feedback loop to calibrate `change_size_penalty`. Single-feature is the honest v1 choice.

This is *attribution-driven retrospective explanation*, NOT DiCE and NOT causal inference. The v1 retrospective counterfactual is a model-explanation statement, not an intervention recommendation. The Autopilot tier (v2+) will introduce intentional N-of-1 experiments to support real causal claims.

### Model module shape (v1)

v1 ships a single `RidgePredictor` class with `fit`, `predict`, `predict_interval`, and `explain` methods. **No Protocol abstraction in v1** — abstracting "for future predictors" is YAGNI when only one model exists. Extract a Protocol when the second predictor actually lands (v2+).

### UI Language Discipline (CRITICAL)

The product is a model-explanation tool, not a coach. Wording matters because it shapes how the user interprets outputs.

**Avoid** (causal-implying language):
- "biggest drivers"
- "what made you tired"
- "you would have felt 7/10"
- "caused"
- "you should"

**Use** (explanation-framed language):
- "top model contributors"
- "patterns the model associated with this rating"
- "model-estimated change in your past data"
- "this is correlation, not proven causation"
- "may reflect unmeasured factors like stress, illness, schedule"

**Mood-first rule (mandatory, but non-blocking UX):** the UI **must not show model output for date D until `feeling[D]` has been logged.** A hyper-health-conscious user may unconsciously conform to model outputs if shown them first. To avoid a "blank app" UX:

- If today's mood is not yet logged, the Streamlit page renders a **compact mood logger at the top** ("Log today's feeling: 1-10, anchored").
- Model outputs for D are hidden until `feeling[D]` lands. Older days' insights remain visible (those moods are already logged and have model outputs).
- Raw mood/sleep timelines remain visible (they don't predict today's state).
- After today's mood is logged, the page refreshes to show the latest eligible retrospective insight.

This preserves the nocebo guardrail without rendering a useless empty page.

### Tripwires — when to fall back

Pre-committed fallback decisions to avoid sunk-cost spirals when something on the critical path resists. Each is non-negotiable and dated to a calendar week.

| Tripwire | Condition | Fallback action |
|---|---|---|
| **Oura ingestion** | End of week 1: Open Wearables not producing usable Oura sleep data in <1 weekend of trying | Drop Open Wearables for Oura; implement direct Oura OAuth2 (authorization-code + refresh tokens) |
| **8 Sleep ingestion** | End of week 2: pyEight not authenticated and returning last night's data reliably | Ship v1 as **Oura-only**. Sleep source reconciliation collapses to identity. Reintroduce 8 Sleep when stable. |
| **Mood transport** | End of week 4: ≥6 of the last 7 evening logs did NOT successfully POST by 11:59pm local | Fall back to a tiny Streamlit-on-home-Wi-Fi mobile-friendly mood form (open in Safari, single tap submit). Defer the Shortcut to v1.1. |
| **Mood compliance** | End of week 8 (4 weeks after API live in week 4): <80% of evenings logged across the trailing 28-day window | **Stop all modeling work.** Fix logging. Compliance is more important than model quality at any stage. |
| **Baseline gate** | End of week 9: ridge walk-forward RMSE > 0.95 × min(rolling-mean RMSE, prior-day RMSE), OR ridge_better_day_count < 65% threshold | Collapse UI to "collecting more data" state. Between week 9 and week 12, increase model signal *without* deliberate sleep restriction: (a) start logging optional context chips (sick / travel / alcohol / unusually stressful) to surface outlier days that explain noise; (b) compare naturally short nights (already observed) vs naturally long nights for pattern visibility; (c) introduce **action-feature logging early** (bedtime time, caffeine cutoff time, dinner time) — these are v2 features but logging them now starts the clock for v2 modeling. **Do NOT deliberately short-sleep** — that's actively harmful guidance for a sleep-conscious user. If the model still doesn't beat baselines after these changes, pivot to anomaly detection or weekly pattern review (D2 options) instead of forcing CF. |
| **8 Sleep mid-build breakage** | Any week before 9: pyEight fails after firmware update | Switch to Oura-only same day; do not pause critical path |

The point is to write down the decision *before* you're in the heat of it, so you don't optimistically push through three more weekends when the right call is to switch strategies.

## Open Questions

1. **Mood-log schema.** MVP locked to {feeling (1-10), energy (1-10 optional), notes (free text optional)}, logged 1x per day in the evening. Open question for v2: is 3x/day (morning/afternoon/evening) worth the friction? Resolve only after 30 days of consistent 1x/day logging — friction tolerance is a personal calibration.
2. **Oura ingestion path.** Open Wearables release notes (0.5.1, May 2026) claim Oura webhooks, but their provider docs are inconsistent and their stack is heavier than expected (Docker Compose with FastAPI + React + Postgres + Redis + Celery; project is pre-1.0 with API churn warning). **Use periodic-pull, not webhooks, in v1** — webhooks need a publicly-reachable HTTPS endpoint, which contradicts local-first. Smoke-test Open Wearables in week 1; if not producing Oura sleep data in <1 weekend, fall back to **direct Oura OAuth2** (authorization-code flow with access + refresh tokens — current Oura developer documentation emphasizes OAuth2, not PAT, for new integrations). Either path is fine; don't over-invest in Open Wearables.
3. **8 Sleep ingestion stability.** `pyEight` is reverse-engineered. Could break on 8 Sleep firmware updates. Build a thin abstraction layer so the ingestion source can swap without changing downstream code. **Maintenance budget:** assume 1-2 weekends per year for pyEight breakage. If 8 Sleep ever ships a CSV export or stable API, switch immediately. **Mid-build contingency:** if pyEight breaks before week 9, ship v1 as **Oura-only** — the sleep source reconciliation collapses to identity (Oura is sole source). Reintroduce 8 Sleep when stable. This protects the critical path.
4. **Confounding handling.** Codex flagged fake causality as a real risk. v1 surfaces "this is a correlation the model found in YOUR past, not a proven cause" framing on every counterfactual output. Real intentional experiments (e.g., "vary dinner timing this week") are an Autopilot-tier feature, post-week-16.
5. **Statistical quality milestones.** At N=30 the only meaningful gate is **"does ridge beat rolling-mean and prior-day baselines under walk-forward evaluation?"** (see Baseline Gating). R² targets at small N are unreliable: low R² can reflect label noise, insufficient behavioral variation, or unmeasured confounders (stress, illness, travel) — not necessarily a wrong feature set. Track R² in `eval.jsonl` for visibility; do not make it a UI claim or a decision criterion in v1.
6. **Nocebo loop guardrails.** UX should never frame predictions as fate ("you WILL feel bad tomorrow"). Always frame as "this is what the data has correlated with in YOUR past — small experiments will tell us what's actually causal." Specific UI rule: confidence labels (low/medium/high) always shown next to predictions; counterfactual labeled "model suggestion, not medical advice."
7. **Mood-log transport.** v1 default: **home Wi-Fi only**. Simpler, no Tailscale dependency, no iOS Shortcut auth fragility. Trade-off: you must remember to log mood before leaving the house, or wait until you return. If this proves untenable after 30 days, upgrade path is Tailscale (Phase 2 — not v1). The iMessage-to-API bridge is an explicit post-v1 option and not in scope. This locks one well-known fragility out of the critical path.

8. **Ingestion architecture decision (week 1):** the architecture diagram lists "Open Wearables periodic-pull (Oura)" but the Tripwires section makes this contingent on a successful 1-weekend smoke test. By end of week 1, this becomes one of: (a) Open Wearables periodic-pull for Oura, or (b) direct Oura OAuth2 with authorization-code + refresh-token flow. Either path is fine; document the chosen one in `README.md` before week 2. Periodic pull is preferred over webhooks in both cases — webhooks require a publicly-reachable HTTPS endpoint, which contradicts the local-first constraint.

- **Week 11:** launchd cron + snapshot backup + macOS local notifications running unattended for 14 days.

  **Minimum viability gates (ALL must be yes for v1 to be operationally viable):**
  1. Mood-logging compliance ≥80% over the trailing 28-day window ending at week 16.
  2. Data pipeline runs unattended (no manual intervention needed beyond mood logging).
  3. No unresolved security/privacy issue (token gating works, snapshots encrypted, no data leaks to logs).
  4. At least one of: (baseline gate passed at any point) OR (weekly pattern review surfaces something useful even without baseline-pass).

  **Quality questions (used to score success beyond minimum):**
  5. Did the system surface at least one retrospective counterfactual at any point in the 16 weeks (gated on baseline-pass + mutable feature sign-stable)?
  6. Did at least one counterfactual change your behavior in the following week?
  7. Did any insight remain useful upon re-reading it 7 days later?

  - All 4 minimum gates pass AND 2-3 quality questions yes → v1 clearly succeeded.
  - All 4 minimum gates pass AND 1 quality question yes → v1 partially succeeded; continue if motivation remains high.

## Distribution Plan

Even personal-use tools need a plan, because hardware fails and engineers move workstations. Local-first applies to *data*; the transport layer (notifications, sync) uses whatever simple local primitives work — no Tailscale, no third-party push services.

- **Repo:** GitHub private repo (this one). Code only — no raw data, no secrets.
- **Secrets:**
  - **Static (1Password + `.env`):** Oura `client_id`/`client_secret`, 8 Sleep email/password, `X-Mood-Token`.
  - **Dynamic (file only, NOT in 1Password):** Oura `access_token`/`refresh_token`/`expires_at` live in `data/secrets/oura_tokens.json` with `chmod 0600`. Oura refresh tokens are **single-use** — every refresh returns a new access+refresh pair and invalidates the prior refresh token. Storing them in 1Password would go stale instantly. Update atomically: write to `oura_tokens.json.tmp`, `fsync`, then `os.replace()` to the real path. Include in encrypted snapshot backups so that restore preserves the active token. **If restored OAuth refresh token fails (e.g., older than ~ months old), re-run `scripts/oura_auth.py` to reauthorize from `client_id`/`client_secret`** — document this in the restore runbook.
  - **8 Sleep:** `pyEight` uses session cookies. Cache them under `data/secrets/eight_session.json` with the same atomic-replace pattern.
  - All `.env` and `data/secrets/*` excluded from git via `.gitignore`.
- **Daily sync:** launchd cron at 8am. Errors logged to `~/Library/Logs/healthhub.log`. Failures send a local macOS notification via `osascript -e 'display notification ...'`. **No third-party push service in v1** — Apple local notifications keep the data path local. **Runtime SLA: nightly job must complete in <120s end-to-end.** Wrapped in a `flock` mutex so retrains can't overlap if a sync runs long.
- **Data backups (snapshot procedure, encrypted, NOT raw rsync):** `data/warehouse.duckdb` is a live database with writers. Backing it up via raw rsync risks copying mid-write state. Snapshot procedure:
  1. Acquire the application file lock (`fcntl.flock` on `data/.healthhub.lock` — see Locking below).
  2. Run `CHECKPOINT;` (DuckDB documented statement; not `PRAGMA checkpoint;`) to flush WAL to disk.
  3. `cp data/warehouse.duckdb data/snapshots/warehouse-{date}.duckdb` (or use `COPY FROM DATABASE` for a physical SQL-level copy if `cp` proves unreliable).
  4. Bundle: the snapshot + that day's `data/raw/{source}/{sleep_date}/*.json` files + the current `data/secrets/oura_tokens.json` (so restore preserves the active refresh token).
  5. **Encrypt the bundle.** v1 default: `age` symmetric encryption with a passphrase stored in 1Password. Alternative: enable Apple Advanced Data Protection on iCloud Drive (provides end-to-end encryption for Drive contents). Either approach is acceptable; encrypted-zip-via-age is simpler and explicit.
  6. Move the encrypted bundle to the iCloud Drive backup folder.
  7. Release the lock.
  8. Retain the last 30 snapshots; prune older.
  - Runs nightly after retrain. iCloud is the single backup target for v1 — Backblaze B2 deferred. **Raw JSON canonicality:** the DuckDB snapshot is canonical for restore. Raw JSON files are retained locally for audit/replay but not guaranteed complete in every nightly snapshot (only that day's JSON is bundled). Weekly full-raw-JSON archive is optional.

- **Locking (Python `fcntl`, not shell `flock`):** macOS does not ship a Linux-style `flock(1)` shell utility by default. Instead, wrap the nightly job in a Python lock:

  ```python
  import fcntl
  with open("data/.healthhub.lock", "w") as lockfile:
      try:
          fcntl.flock(lockfile, fcntl.LOCK_EX | fcntl.LOCK_NB)
      except BlockingIOError:
          # Another instance is running; exit quietly.
          sys.exit(0)
      # ... do work ...
  ```

  Alternative: add `filelock` as a dependency (cleaner cross-platform, ~5 lines of code).

- **Filesystem permissions (set by `scripts/setup_permissions.py` in v1; NOT deferred to bootstrap.sh):**
  ```text
  chmod 700 data/
  chmod 700 data/secrets/
  chmod 700 data/quarantine/
  chmod 700 data/snapshots/
  chmod 600 data/warehouse.duckdb
  chmod 600 data/secrets/*.json
  ```
  Run `scripts/setup_permissions.py` after every `git pull` (or wire it into a git hook). The `Justfile` / `bootstrap.sh` v1.1 polish wraps this; the underlying permissions are v1, not polish. FileVault enabled on the Mac is also a v1 requirement (full-disk encryption at rest).
- **Reproducible setup (v1.1 polish):** `pyproject.toml` + `uv` for dependencies. README runbook with bootstrap steps. **`Justfile` and a one-shot `bootstrap.sh` are explicit polish items deferred to v1.1 (after week 14)** — README is sufficient for a single-user system until something has been worth re-setting-up.
- **Recovery procedure (kept in v1, week 14):** documented in `README.md`. Verify the snapshot restore path once in week 14 — restore a snapshot to a clean directory, run the read-only Streamlit against it, confirm yesterday's insights render the same numbers. For a local-first health-data project, backup integrity is part of the product, not polish.
- **Network access:** home Wi-Fi only. No Tailscale in v1. No public exposure.

When/if this becomes shareable with friends: open-source the repo under MIT, document the bootstrap path, accept that anyone running it needs their own device credentials and is fully responsible for their own data. No hosted version. Docker image only built then, not before.
