# S02 Mood API Loop Playbook

Context: This `markdown_playbook_v1` playbook is an autonomous S02 Mood API loop plan, not an execution log. It covers only the local-first mood API loop described in `docs/gstack/s02-mood-api-autoplan.md`, constrained by the autonomous policy in `docs/briefs/s02-mood-api.autonomous-brief.md`, the Health Data Hub v1 invariants in `docs/gstack/health-data-hub-office-hours.md`, and the parser contract in `automation/task_packs/gstack_design_to_po_playbook/corpus/markdown_playbook_v1_contract.md`. No plan-orchestrator execution, command output, or verification pass is claimed by this document.

## 1. Phase Overview

This playbook plans seven narrow execution items for S02:

- Rows 01 and 02 establish deterministic foundations: mood-date attribution, request and response schemas, and testable dependency seams using fake runtime values.
- Row 03 implements the API route surface and security boundary before persistence is connected.
- Row 04 connects mood persistence only through a compatible S01 warehouse helper, with blocker conditions if the helper interface is absent, unclear, or incompatible.
- Row 05 closes deterministic tests without real secrets, real local network behavior, runtime data, external services, or production health data.
- Rows 06 and 07 produce autonomous security and privacy review artifacts plus final source-backed checks.

Active manual gates are forbidden for this autonomous S02 run. Rows that normally trigger manual signoff because they involve security boundaries, secrets, privacy, persistence ambiguity, external dependencies, or production-data risk use autonomous evidence gates and explicit blocker conditions instead. No manual gate row is emitted, no manual gate marking command is authorized, and no human approval is claimed.

Unresolved security, secret, production-data, dependency, schema, helper-interface, external-service, or customer-facing ambiguity blocks execution or requires new authority. It must not be resolved by widening write roots, inventing repository facts, changing package manifests, editing warehouse schema, touching runtime data, or weakening Health Data Hub v1 scope.

## 3. Phase Details

### 01 Foundation

Purpose:

- Implement the mood-date attribution rule as a pure deterministic helper before any route or persistence work.
- Preserve the design rule that late-night logs from 00:00 through before 04:00 local time are attributed to the prior local date.
- Keep timezone handling explicit through a supplied home timezone and `zoneinfo`.

Allowed writes:

- `src/api/mood_date.py`
- `tests/test_mood_date.py`

Read-only or uncertain integration surfaces:

- `docs/gstack/health-data-hub-office-hours.md` is the source for the 04:00 local cutoff and DST-safe `zoneinfo` requirement.
- Handler-level source of the home timezone remains uncertain. Row 01 must not invent a runtime configuration policy.

Verification command:

- `python -m pytest tests/test_mood_date.py -q`

Expected verification coverage:

- 23:30 local resolves to the same date.
- 00:30 local resolves to the previous date.
- 03:59 local resolves to the previous date.
- 04:01 local resolves to the current date.
- A DST transition case resolves through `zoneinfo` without crashing or producing an off-by-one date.

Gate disposition:

- No active manual gate is emitted.
- This row avoids normal manual-signoff triggers because it does not touch secrets, production data, runtime network behavior, warehouse schema, or external services.

Blocker conditions:

- Block if implementation attempts to read real runtime configuration values.
- Block if implementation requires writing outside the allowed files.
- Block if timezone policy beyond the pure helper requires a new product decision.

## 5. Risks And Contingencies

Dependency availability uncertainty:

- Risk: FastAPI, Pydantic, pytest, or slowapi may be absent or incompatible.
- Contingency: Block if fixing dependency availability requires package manifest edits. Do not add unapproved custom replacements for source-specified dependencies.

S01 warehouse helper interface uncertainty:

- Risk: `src/warehouse/warehouse.py` may be absent, incompatible, or may not expose a clear append-only mood writer.
- Contingency: Block Row 04. Do not duplicate the writer in `src/api/`, do not change schema, and do not write production data.

S01 quarantine pathway uncertainty:

- Risk: The S01 quarantine helper may be absent or unsuitable for API validation failures.
- Contingency: Reuse it only if source-compatible and testable without raw tracked payloads. Otherwise block or require new authority.

Home timezone configuration source uncertainty:

- Risk: The pure resolver needs `home_tz`, but the route-level runtime source for home timezone is not fully specified.
- Contingency: Implement the pure helper with explicit timezone input. If handler configuration requires a new policy, block or require new authority.

Read placeholder response-shape uncertainty:

- Risk: S02 source material authorizes placeholder read routes but does not fully specify their response body.
- Contingency: Keep placeholders minimal, protected, and non-claiming. Block if a downstream expectation requires model outputs, predictions, recommendations, counterfactual computation, or causal language.

Real iOS Shortcut and home-network behavior not repo-verified:

- Risk: Real phone-to-Mac behavior, local network permission, and home Wi-Fi source IP behavior cannot be verified by deterministic repo tests.
- Contingency: Do not require real-device or real-network verification in S02. Use simulated client hosts and fake tokens. Treat real-world setup as out of scope for this playbook.
